02 / The theory behind it

Four conditions make a deadlock possible.

In the classic operating-systems model, all four conditions must hold at the same time for a deadlock to occur.

CONDITION 01

Mutual exclusion

A resource with an exclusive lock can be held by only one transaction at a time.

CONDITION 02

Hold and wait

A transaction holds one lock while waiting for another resource.

CONDITION 03

No preemption

A lock is not simply taken away while its transaction is using it.

CONDITION 04

Circular wait

T1 waits for a resource held by T2, while T2 waits for a resource held by T1.

03 / Getting things moving

Detect it. Break the cycle. Continue.

Database systems use different policies, but a common recovery approach is to detect the conflict and roll back a transaction.

⌕

1. Detect the cycle

A wait-for graph or another method can identify transactions waiting in a loop.

↶

2. Roll back a transaction

The database selects a transaction to abort, releasing its locks and breaking the cycle.

✓

3. Resume safely

The remaining transaction proceeds. The rolled-back work may be retried.

04 / Real-world case study

Two bank transfers compete for the same accounts.

Scenario: Imagine two customers making transfers at nearly the same time. Transaction T1 needs to update Account A and then Account B. Transaction T2 needs to update Account B and then Account A. The database uses locks to stop both transfers from changing the same account record at once.

How deadlock happens: T1 locks Account A while T2 locks Account B. T1 then waits for B, and T2 waits for A. Each holds a lock the other needs, so neither can continue. This creates a circular wait: T1 → T2 → T1.

Why this fits deadlock: Both transactions hold resources while waiting for each other. Neither can finish and release its lock, so the cycle remains blocked. The database may detect the cycle, roll back one transaction, allow the other to complete, and retry the rolled-back transaction if appropriate.

This is an illustrative banking scenario, not a claim about a specific bank incident. Actual database products use different locking and recovery policies.
